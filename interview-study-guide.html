Expert-level C#

Language mechanics, concurrency, memory, and correctness.

Official references: C# async programming · C# 13 changes · Generic variance · Memory diagnostics

Q01What actually happens when you use async and await in C#?

Model answer

An async method runs synchronously until it reaches an await whose operation is incomplete. The compiler transforms the method into a state machine and arranges a continuation; await does not automatically create a thread. For asynchronous I/O, the thread can return to the pool while the operation is pending. CPU work still needs CPU time. In an ASP.NET Core request, I use async I/O end to end, pass cancellation tokens, and avoid .Result or .Wait(), which block threads and can cause thread-pool starvation.

Follow-up + answer cue

Would you wrap a database call in Task.Run? → No: use the provider's async API. Task.Run adds scheduling and does not make blocking I/O scalable.

Avoid this mistake: Saying async means parallel, or claiming every await switches threads.

#01
Q02How do Task, ValueTask, cancellation, and bounded concurrency differ?

Model answer

Task is the default representation of asynchronous completion and can be awaited repeatedly. ValueTask can avoid allocations when operations frequently complete synchronously, but has consumption restrictions and should follow measured need; generally await it once. Cancellation is cooperative: pass a CancellationToken and honor it in downstream work. Task.WhenAll coordinates already-started operations but does not limit concurrency. For thousands of requests, use a bounded worker pool, Channel, SemaphoreSlim, or an appropriate parallel API with an explicit limit.

Follow-up + answer cue

What happens if one task fails? → WhenAll completes after all tasks finish; awaiting it throws. Inspect the combined task's Exception to examine all failures, and define any sibling-cancellation policy.

Avoid this mistake: Starting unbounded work, using async void outside event handlers, or treating cancellation as an automatic rollback.

#02
Q03Explain value types, reference types, records, equality, and boxing.

Model answer

A value-type variable contains its value; a reference-type variable holds a reference to an object. Assignment copies the value or the reference respectively. Storage is contextual: structs are not always on the stack. A record class is a reference type with generated value-oriented equality; a record struct is a value type. Neither guarantees deep immutability. Boxing wraps a value type as an object or compatible interface and can allocate. For dictionary keys, equality and hash codes must agree, and equality-relevant state should remain stable while stored.

Follow-up + answer cue

Would you use a record for every EF entity? → Usually no; persistent entities have identity and mutable lifecycle concerns that differ from value objects.

Avoid this mistake: Assuming record with-expressions deeply clone nested collections.

#03
Q04When would you use Span<T>, Memory<T>, IDisposable, and IAsyncDisposable?

Model answer

Span<T> is a ref struct view over contiguous memory, useful for slicing and parsing without copying. It cannot be stored in ordinary heap objects. Memory<T> can be held across asynchronous operations, while its backing storage must remain valid. C# 13 relaxes some ref-struct restrictions in async methods, but a span cannot remain live across await. IDisposable releases resources deterministically with using; IAsyncDisposable supports asynchronous cleanup with await using. Garbage collection reclaims managed memory, not timely release of connections or handles.

Follow-up + answer cue

Can a pooled buffer be returned before an awaited operation finishes? → No; another caller could overwrite it while it is still in use.

Avoid this mistake: Saying Span always allocates on the stack, or relying on GC to close scarce resources.

#04
Q05How would you make shared state thread-safe, and why is ConcurrentDictionary not enough by itself?

Model answer

First avoid shared mutable state or confine ownership. For a simple counter, Interlocked provides atomic operations; lock protects a multi-step invariant in synchronous code. A concurrent collection protects its own operations, not arbitrary workflows spanning multiple calls or objects. GetOrAdd factories may run more than once, so they must not perform non-idempotent external work. For async coordination, use SemaphoreSlim.WaitAsync with release in finally. In .NET 9/C# 13, System.Threading.Lock is another synchronous lock option.

Follow-up + answer cue

Does a process-local lock prevent duplicate payments across replicas? → No. Use durable uniqueness, idempotency keys, and provider-side safeguards.

Avoid this mistake: Holding locks during network calls, awaiting inside lock, or assuming a thread-safe container makes its mutable values thread-safe.

#05
Q06How do generics, covariance, and contravariance affect API design?

Model answer

Generics provide reusable, statically checked code and can avoid boxing value types that would otherwise be stored as object. Constraints express what operations a type parameter supports. Covariance permits a producer of a derived reference type to be used as a producer of a base type, such as IEnumerable<string> as IEnumerable<object>. Contravariance permits a consumer of a base type where a consumer of a derived type is needed, such as Action<object> as Action<string>. Variance applies to appropriately declared interfaces and delegates and reference-type conversions; mutable List<T> is invariant.

Follow-up + answer cue

Why is List<string> not a List<object>? → That would allow adding a non-string object and violate the original list's contract.

Avoid this mistake: Assuming generic variance applies to value types or every generic collection.

#06
Q07How do you handle exceptions without losing information or hiding failure?

Model answer

Catch exceptions at a boundary where you can recover, translate, compensate, or add useful context. Use throw; to rethrow while preserving the original stack, rather than throw ex;. Treat expected validation failures as explicit results when that improves clarity; reserve exceptions for exceptional or framework-defined failures. Use finally or using for cleanup. Cancellation is normally a distinct outcome, not a server error. Log once at the responsible boundary with structured context, while preserving inner exceptions when translating.

Follow-up + answer cue

Should a catch-all return an empty list? → Only if the contract explicitly defines that fallback; otherwise it disguises failure as valid data.

Avoid this mistake: Swallowing exceptions, exposing internal messages to clients, or repeatedly logging the same error at every layer.

#07
Q08How would you investigate a memory leak or latency spikes in a managed .NET service?

Model answer

Correlate latency with allocations, GC collections and pauses, heap growth, thread-pool queues, and dependency latency. Compare a steady-state baseline under representative load, then use traces and dumps to inspect retained objects and their roots. Garbage collection cannot free objects still referenced by static collections, unbounded caches, event subscriptions, or long-lived scopes. High allocation rates can cause pressure even without a leak. Fix ownership and bound caches before introducing pooling or manual GC calls; measure the change.

Follow-up + answer cue

Does high process memory always mean a leak? → No; heap reservation, native memory, caching, and workload growth also affect the process footprint.

Avoid this mistake: Calling GC.Collect on each request or optimizing allocations without identifying the actual latency bottleneck.

.NET 8 / 9

Know the requested versions and explain migration decisions with evidence.

Official references: .NET 8 overview · .NET 9 overview · ASP.NET Core 9 changes

Q09Which changes in .NET 8 and .NET 9 would you discuss in an interview?

Model answer

I separate language, runtime, framework, and package versions. .NET 8 shipped with C# 12, including primary constructors and collection expressions, and expanded ASP.NET Core Native AOT support. .NET 9 pairs with C# 13, adding features such as params collections and improved lock support. .NET 9 also adds LINQ CountBy and AggregateBy; ASP.NET Core 9 introduces built-in OpenAPI document generation through Microsoft.AspNetCore.OpenApi. I connect each feature to a concrete benefit rather than listing release notes.

Follow-up + answer cue

Does built-in OpenAPI generation include Swagger UI automatically? → No; an interactive UI is a separate integration.

Avoid this mistake: Attributing a newer feature to .NET 8 or assuming changing the language version upgrades runtime APIs.

#09
Q10How would you safely upgrade a production service from .NET 8 to .NET 9?

Model answer

Inventory target frameworks, SDK pinning, NuGet packages, EF providers, deployment images, and third-party compatibility. Read breaking changes and update a representative service first. Run unit, integration, contract, authentication, serialization, and migration checks against realistic dependencies. Compare latency, throughput, allocation, and startup baselines; then use a gradual rollout with observable rollback criteria. Keep database changes backward compatible across the rollout. .NET 8 is an LTS release and .NET 9 is STS; check the current support policy when planning, rather than assuming the older version always has longer remaining support.

Follow-up + answer cue

Is changing TargetFramework sufficient? → No; build agents, deployment runtime, dependencies, and behavioral compatibility also matter.

Avoid this mistake: Treating successful compilation as proof that the upgrade is safe.

#10
Q11When would you choose Native AOT instead of the usual JIT deployment?

Model answer

Native AOT compiles ahead of time and can improve startup and memory characteristics, which may suit short-lived processes or constrained services. The tradeoffs include build complexity, platform-specific output, and limits around dynamic code generation and reflection-dependent libraries. Source generation can replace some runtime discovery, but not every application or package is compatible. I validate the actual framework surface, resolve trimming/AOT warnings, and measure the production workload. A long-running service may benefit sufficiently from the JIT that AOT adds little value.

Follow-up + answer cue

Would you enable AOT just because a benchmark is faster? → No; compare representative cold start, steady-state throughput, memory, diagnostics, and maintenance costs.

Avoid this mistake: Claiming AOT makes every application faster or is merely another publish flag without compatibility work.

ASP.NET Core

Request flow, API boundaries, and production behavior.

Official references: Middleware and ordering

Q12How does the middleware pipeline work, and why does ordering matter?

Model answer

Middleware can inspect a request, invoke the next component, short-circuit, and act on the response as control returns. Earlier middleware wraps later components. Exception handling should be early enough to observe downstream failures. Endpoint-aware CORS and authorization need routing metadata; authentication must establish the principal before authorization evaluates access. Static-file placement affects whether those files are public. I make security-sensitive ordering explicit and verify representative requests instead of relying on template conventions.

Follow-up + answer cue

Can middleware change response headers after the response starts? → Generally no; set them before writing or use an appropriate OnStarting callback.

Avoid this mistake: Assuming every request reaches every middleware component.

#12
Q13Would you choose controllers or Minimal APIs, and where does validation belong?

Model answer

Both can support production APIs. Minimal APIs offer concise routing and endpoint composition; controllers provide familiar MVC conventions, filters, and model binding. I choose based on API complexity, team consistency, extension needs, and target-version capabilities. Request validation handles malformed input; application and domain logic enforce business rules. With [ApiController], model-state errors can produce automatic 400 responses. Minimal APIs in .NET 8/9 need an explicit validation strategy rather than assuming identical controller behavior. Return DTOs, not persistence entities.

Follow-up + answer cue

Where would you check that a customer can cancel an order? → In the application/domain flow after authorization; a DTO annotation cannot enforce a lifecycle rule.

Avoid this mistake: Putting business rules only in UI validation, or assuming Minimal APIs imply a throwaway architecture.

#13
Q14How would you make errors and background work reliable in ASP.NET Core?

Model answer

Use centralized exception handling, map known application failures to documented responses, and return consistent Problem Details with a correlation identifier. Log details internally without leaking stack traces or secrets. Do not start untracked fire-and-forget tasks using request-scoped services: the request scope may end and the process may restart. Use a hosted service with explicit scopes for local work; use a durable queue and worker when the work must survive a restart. Propagate cancellation where appropriate and define graceful shutdown behavior.

Follow-up + answer cue

Should every exception become HTTP 400? → No; distinguish invalid input, conflicts, access failures, transient dependency failures, and unexpected server faults.

Avoid this mistake: Returning HTTP 200 with an error string, or assuming an in-memory background queue is durable.

REST API development

HTTP semantics, usable contracts, and safe retries.

Official references: HTTP semantics — RFC 9110

Q15What makes a good REST-style API beyond using JSON over HTTP?

Model answer

Model resources with stable identifiers, use HTTP method semantics deliberately, and make each request carry the context needed to process it. GET is safe and idempotent; PUT and DELETE are idempotent in intended effect; POST and PATCH are not inherently idempotent. Use meaningful status codes: 201 with Location for creation, 202 for accepted unfinished work, and 204 when there is no response body. Document validation and error formats. Strict REST also includes constraints such as a uniform interface and hypermedia; many practical HTTP APIs implement only a subset.

Follow-up + answer cue

Must repeated DELETE requests return the same status? → No; idempotency concerns the intended server effect, not identical responses.

Avoid this mistake: Calling any JSON endpoint RESTful or mutating business state through GET.

#15
Q16How would you design pagination, evolution, and caching for a public API?

Model answer

Use bounded page sizes and a deterministic sort with a unique tie-breaker. Offset pagination is simple but becomes expensive or unstable as data changes; cursor/keyset pagination is often better for large feeds. Favor additive, compatible contract changes and define a versioning/deprecation policy for breaking changes. Cache only where the data and authorization model permit it; use Cache-Control and validators such as ETag. Keep user- or tenant-specific representations from entering a shared public cache.

Follow-up + answer cue

Does a cursor guarantee a frozen snapshot? → No; that requires explicit snapshot or consistency semantics.

Avoid this mistake: Returning an unbounded list, changing field meaning without versioning, or caching private responses by URL alone.

#16
Q17How do you prevent lost updates and duplicate creates?

Model answer

For updates, expose a version or ETag and require a precondition such as If-Match; reject a failed precondition with 412. Enforce the version atomically in the data store. For operations such as order creation, accept an idempotency key scoped to the caller and operation, persist a request fingerprint plus result, and enforce uniqueness. A repeated identical request returns the recorded outcome; key reuse with different input must be rejected. Define expiration and in-progress behavior, including recovery after a crash.

Follow-up + answer cue

What if the server commits but the client times out? → The client retries with the same key and receives or reconciles the existing outcome.

Avoid this mistake: Performing a non-atomic check-then-insert or generating a new idempotency key for every retry.

Microservices Architecture

Boundaries and operational tradeoffs before service count.

Official references: Domain analysis for microservices

Q18When would you choose microservices, and when would you keep a modular monolith?

Model answer

Microservices can help when business capabilities need independent deployment, scaling, ownership, or isolation. They also introduce network failure, distributed data consistency, contract evolution, and substantial operational work. I start with business boundaries, team structure, and measurable constraints. A modular monolith is often preferable when a small team needs fast change and strong local transactions. Extract a service when there is a clear boundary and benefit, not simply because a codebase has grown.

Follow-up + answer cue

Is one service per database table a good boundary? → Usually no; organize around cohesive business capabilities and their invariants.

Avoid this mistake: Equating microservices with clean code or assuming more services automatically improve scalability.

#18
Q19How should services own data and collaborate without becoming a distributed monolith?

Model answer

Each service owns its data model and write rules. Other services use contracts or consume published facts rather than directly changing its tables. Physical databases may share infrastructure, but ownership and access boundaries remain explicit. Use synchronous calls when an immediate answer is necessary; use asynchronous events for decoupled reactions and replicated read models. Avoid long synchronous chains and shared business libraries that force lockstep deployments. Accept and expose data freshness where eventual consistency is part of the design.

Follow-up + answer cue

How would you build a cross-service report? → Use a reporting projection or analytical pipeline with explicit freshness rather than runtime joins across private tables.

Avoid this mistake: Sharing one schema and coordinating every release while calling the result independent services.

#19
Q20How do you stop a failing dependency from taking down the whole system?

Model answer

Set timeouts within an overall request budget; limit concurrency; and apply bounded retries with backoff and jitter only to transient, safe-to-retry operations. Circuit breakers stop repeated calls to a failing dependency, while bulkheads isolate resource exhaustion. Use IHttpClientFactory or properly managed long-lived clients for outbound HTTP. Add distributed traces, latency/error metrics, and structured logs to identify where time is spent. Define degraded behavior that remains correct, and test partial failure rather than just happy-path throughput.

Follow-up + answer cue

Can retries worsen an outage? → Yes; retries at several layers multiply traffic. Assign ownership and a total retry budget.

Avoid this mistake: Retrying every exception forever or silently returning stale data where correctness forbids it.

Event-Driven Architecture

Delivery guarantees, transactions, and business recovery.

Official references: Transactional outbox architecture

Q21How do commands, events, queues, and publish/subscribe differ?

Model answer

A command asks a particular capability to do something and may be rejected, such as ReserveInventory. An event describes a fact that already happened, such as InventoryReserved, and can have multiple independent consumers. A work queue commonly distributes tasks among competing consumers; publish/subscribe delivers to independent subscriptions, each of which may itself have competing consumers. Choose based on intent and topology. Specify delivery, retention, retry, and ordering behavior; the broker product name alone does not define the contract.

Follow-up + answer cue

Is OrderCreated a request to charge a card? → No; a payment workflow decides whether that fact should trigger a payment command.

Avoid this mistake: Naming imperative commands as past-tense events while requiring exactly one specific consumer to act synchronously.

#21
Q22Explain the transactional outbox and how you handle duplicate messages.

Model answer

Save the business change and an outbox event in the same database transaction. A relay publishes committed outbox records and marks progress. If it crashes after publishing but before recording success, it may publish again, so consumers must tolerate duplicates. Persist a processed-message identifier and the consumer's business changes in one local transaction, protected by uniqueness. External effects need their own idempotency or reconciliation. The outbox closes the database-to-broker gap; it does not give universal exactly-once side effects.

Follow-up + answer cue

What if the broker is down for an hour? → Retain the outbox, retry with limits, monitor backlog age, and recover when delivery resumes.

Avoid this mistake: Saving data and then publishing as two unrelated operations, or marking a message processed before its business work commits.

#22
Q23How do sagas, event ordering, schema evolution, and event sourcing fit together?

Model answer

A saga coordinates a business process across local transactions, using orchestration or choreography and compensating actions when needed. Compensation is a business action, such as issuing a refund, and may itself fail. Preserve ordering where required, often per aggregate key, and use versions to detect stale or missing events. Evolve schemas with compatible fields and explicit versioning rules. Event sourcing stores domain history as the source of truth; ordinary event-driven integration does not require it. Plan dead-letter handling and controlled replay.

Follow-up + answer cue

Can you always undo a saga step? → No; shipped goods or sent emails require business resolution, not a database rollback.

Avoid this mistake: Confusing integration events with event sourcing, or promising global ordering without explaining cost and broker guarantees.

Entity Framework Core

Query shape, units of work, and concurrency.

Official references: Efficient querying · DbContext lifetime · Concurrency conflicts

Q24What is DbContext, how long should it live, and can you run concurrent queries on it?

Model answer

DbContext represents a short-lived unit of work: it tracks entities, coordinates queries, and persists changes. In a typical web app it is scoped to a request, but the actual boundary should match the unit of work. It is not thread-safe, and EF Core does not support parallel operations on the same instance. Await an operation before starting another, or use separately created contexts for independent work. Do not keep a context as a singleton or let tracked entities accumulate indefinitely.

Follow-up + answer cue

Can Task.WhenAll run two queries on one context? → No. Use sequential awaits or separate contexts when independent operations justify concurrency.

Avoid this mistake: Assuming async operations make DbContext safe for parallel access.

#24
Q25An EF endpoint is slow. What would you inspect and change first?

Model answer

Inspect generated SQL, query counts, execution plans, rows transferred, and time spent outside the database. Project only required fields, filter and paginate before materialization, and use no-tracking queries when returning read-only entities. Watch for N+1 lazy-loading calls and large joins from multiple collection Includes. Split queries can reduce cartesian expansion but add round trips and may observe changes between queries. Index for actual predicates and ordering. Measure the resulting plan and end-to-end latency before adding caching.

Follow-up + answer cue

Does AsNoTracking speed up a pure scalar DTO projection? → Often there are no entity instances to track already; query shape and SQL still matter.

Avoid this mistake: Calling ToList before filtering, or using Include everywhere without measuring row multiplication.

#25
Q26How would you implement optimistic concurrency and safe database migrations?

Model answer

Configure a concurrency token, such as SQL Server rowversion. EF includes the original token in the update/delete predicate; if no expected row is affected, SaveChanges throws DbUpdateConcurrencyException. Handle it by reporting a conflict or applying an explicit merge/reload policy rather than blindly overwriting. A supported provider normally wraps one SaveChanges call in a transaction. Use explicit transactions when coordinating multiple saves. For deployments, review migration SQL and use an expand/contract rollout with controlled execution, backups, and a recovery plan.

Interview example · explanatory excerpt
// Entity excerpt; configure other fields and the DbContext separately.
public class Order
{
    public int Id { get; set; }
    public string Status { get; set; } = "Pending";

    [System.ComponentModel.DataAnnotations.Timestamp]
    public byte[] Version { get; set; } = Array.Empty<byte>();
}
// SQL Server provider maps Version as a rowversion concurrency token.
Follow-up + answer cue

Is rowversion a date/time value? → No; it is a database-generated binary version marker, not a timestamp you can display as a date.

Avoid this mistake: Running competing startup migrations from every replica or silently retrying a user conflict with stale values.

LINQ

Execution boundaries and provider behavior.

Official references: LINQ query execution

Q27What is the difference between IEnumerable<T> and IQueryable<T>?

Model answer

IEnumerable<T> exposes iteration; LINQ-to-Objects operators execute .NET delegates while enumerating. IQueryable<T> also carries an expression tree and provider that may translate operations into another query language, such as SQL. IQueryable does not inherently mean database or async. Keep translatable filtering, ordering, and projection on the provider side. AsEnumerable switches subsequent operators to LINQ-to-Objects without itself materializing the query; ToList executes and buffers it. Translation support depends on the provider and version.

Follow-up + answer cue

Does returning IQueryable from a repository have a cost? → Yes; it can expose provider semantics and defer query execution beyond intended boundaries.

Avoid this mistake: Assuming every C# method used in a query can be translated to SQL.

#27
Q28Explain deferred execution and the danger of multiple enumeration.

Model answer

Many LINQ operators build a query that runs only when enumerated. Enumerating twice can repeat expensive work, query the database twice, or observe different source data. Some operators buffer, and terminal operations such as ToList or Count execute immediately. Decide whether you want a live query or a materialized snapshot. Do not return a deferred database query after disposing its context. Materialize only after limiting the data, when reuse or a stable in-memory result justifies the allocation.

Follow-up + answer cue

Is deferred execution always streaming? → No; an operator such as OrderBy must collect data before yielding sorted output.

Avoid this mistake: Calling Count and then foreach over an expensive sequence without considering two executions.

#28
Q29How would you write a paginated query and choose between Select, SelectMany, Any, and Count?

Model answer

Select maps each item to one result; SelectMany flattens nested sequences. Any expresses an existence check and can stop early; use Count when you need the number. For database queries, let the provider translate the intent and inspect the SQL. A paginated query needs a stable order and a maximum size. A keyset predicate over a unique ID is simple when that ID is the desired ordering; compound sorting needs a compound cursor. Projection keeps the transferred payload small.

Interview example · explanatory excerpt
// Inside an async method, using Microsoft.EntityFrameworkCore.
// Assumes db.Orders, lastId, and ct are available.
var page = await db.Orders
    .Where(o => o.Id > lastId)
    .OrderBy(o => o.Id)
    .Select(o => new { o.Id, o.Status })
    .Take(50)
    .ToListAsync(ct);
Follow-up + answer cue

When do First and Single differ? → First needs at least one match; Single also asserts there is only one. The OrDefault versions allow zero but SingleOrDefault still rejects multiple matches.

Avoid this mistake: Using Single as a substitute for a database uniqueness constraint.

SQL Server

Plans, isolation, and set-based reasoning.

Official references: SQL Server index design · Transaction isolation

Q30How do you diagnose and improve a slow SQL Server query?

Model answer

Capture the actual query, parameters, execution plan, logical reads, duration, and blocking. Use Query Store where available to compare plans and regressions. Check estimates versus actual rows, statistics, scans, lookups, spills, and parameter-sensitive behavior. Design indexes around selective predicates, joins, and ordering; included columns may cover a query without expanding the index key. A sargable date range often works better than wrapping an indexed column in a function. Every extra index adds write and storage cost, so verify the workload benefit.

Follow-up + answer cue

Is an index seek always better than a scan? → No; reading much of a table may make a scan cheaper.

Avoid this mistake: Adding indexes blindly or treating one execution with a warm cache as a reliable benchmark.

#30
Q31Explain isolation levels, deadlocks, and why NOLOCK is not a general performance fix.

Model answer

Isolation determines which concurrent changes a transaction can observe. SQL Server READ COMMITTED uses locks by default, or statement-level row versions with READ_COMMITTED_SNAPSHOT enabled. SNAPSHOT offers transaction-level versioned reads; SERIALIZABLE protects against phantoms with stronger locking and can reduce concurrency. Deadlocks form a cycle of resource waits; the database chooses a victim. Keep transactions short, access resources in consistent order, and retry the entire safe transaction with a bound. NOLOCK permits dirty and inconsistent reads; it does not mean no locks of any kind.

Follow-up + answer cue

Does snapshot isolation eliminate write conflicts? → No; concurrent writes still need conflict handling and invariant enforcement.

Avoid this mistake: Using NOLOCK on financial totals or retrying just the failed statement in a multi-statement transaction.

#31
Q32Write a query for the most recent order per customer and explain correctness.

Model answer

Use ROW_NUMBER partitioned by customer and ordered by the order date descending, with a unique tie-breaker such as OrderId. Filtering row number 1 returns one deterministic order per customer. A MAX(OrderDate) joined back to the table can return multiple rows when dates tie. Consider an index starting with CustomerId and the sort columns for the actual access pattern. If the requirement is all tied latest orders, use a ranking rule that deliberately retains ties instead.

Interview example · explanatory excerpt
WITH Ranked AS (
    SELECT OrderId, CustomerId, OrderDate, Total,
           ROW_NUMBER() OVER (
               PARTITION BY CustomerId
               ORDER BY OrderDate DESC, OrderId DESC
           ) AS rn
    FROM dbo.Orders
)
SELECT OrderId, CustomerId, OrderDate, Total
FROM Ranked
WHERE rn = 1;
Follow-up + answer cue

How would you include customers with no orders? → Start from Customers and use LEFT JOIN or OUTER APPLY, preserving unmatched customers.

Avoid this mistake: Omitting a tie-breaker and assuming the same row will always win.

NoSQL databases

Choose a data model from access patterns and guarantees.

Official references: MongoDB data modeling

Q33When would you choose a NoSQL database instead of SQL Server?

Model answer

Start with access patterns, consistency, transaction boundaries, data volume, and operational skills. Relational storage is strong for relationships, constraints, multi-row transactions, and flexible querying. A document database may fit aggregates commonly read together; key-value storage may fit lookup or caching; graph storage may fit relationship traversal. NoSQL is a family of systems, not one consistency model. Some support transactions and strong reads under particular configurations. Prototype representative reads, writes, indexes, and failure behavior before choosing.

Follow-up + answer cue

Does flexible schema mean no schema design? → No; validation, versioning, and migration still exist even when the database enforces less.

Avoid this mistake: Choosing NoSQL merely because the data is JSON or assuming it is always faster.

#33
Q34How do you choose document boundaries, partition keys, and consistency?

Model answer

Embed data read and changed together when size and growth are bounded; reference data with independent lifecycles or unbounded fan-out. Choose partition keys that distribute traffic and support common queries without excessive cross-partition work. Watch for hot tenants or time-based keys concentrating writes. In a network partition, CAP highlights a tradeoff between linearizable consistency and availability; it is not a blanket choose-any-two rule for all operation. State the actual database guarantees, read/write configuration, and acceptable staleness for each use case.

Follow-up + answer cue

Q35Explain transient, scoped, and singleton lifetimes. What is a captive dependency?

Model answer

Transient creates an instance each time the service is resolved; scoped creates one per scope; singleton is reused for the container's lifetime. In ASP.NET Core, a request normally gets a scope. Q45When would you use Strategy, Factory, Adapter, and Decorator?

Q48What is the difference between authentication, authorization, OAuth 2.0, OIDC, and JWT?

Model answer

Authentication establishes who the caller is; authorization decides which actions that caller may perform. OAuth 2.0 defines delegated authorization mechanisms for obtaining access tokens. OpenID Connect adds an identity layer, including an ID token for the client. JWT is a token format, not a login protocol, and OAuth access tokens need not be JWTs. An API expects an access token issued for that resource, not an ID token intended for the client. Most signed JWTs are readable by their holder; signing does not encrypt claims.

Follow-up + answer cue

Can decoding a JWT authenticate a user? → No; the token must be validated under a trusted issuer and the intended token use.

Avoid this mistake: Using OAuth, OIDC, and JWT as interchangeable terms.

Q56How do any, unknown, never, interfaces, and type aliases differ?

Q71Why can Context cause many rerenders, and how would you reduce them?

Model answer

Consumers update when their provider's value changes according to React's comparison behavior. A newly created object can change identity on every provider render, even if its contents seem similar. Split unrelated contexts, place providers near consumers, and stabilize values/functions where that demonstrably helps. High-frequency or selectively consumed data may fit a store with subscriptions/selectors better. memo does not block updates caused by a context the component consumes.

Follow-up + answer cue

Would one giant AppContext simplify a large application? → It can centralize coupling and broad updates, so split by coherent responsibility.

Avoid this mistake: Assuming a stable provider component means its object value is stable.

Q72What are the rules for reducers, immutable updates, selectors, and async work?

Model answer

Reducers should compute the next state from the previous state and action without external side effects. Redux Toolkit uses Immer so reducer code can look mutative while producing immutable results under its draft rules. Keep state serializable where practical, normalize shared entity data, and derive values with selectors rather than storing redundant copies. Handle asynchronous work outside reducers using appropriate query/middleware tools. Model loading and failure explicitly, and invalidate or update cached data after mutations.

Follow-up + answer cue

Is assigning state = newValue enough inside an Immer reducer? → No; return the replacement or mutate the draft correctly.

Avoid this mistake: Fetching inside a reducer or mutating stored objects outside the supported update mechanism.

Q73What belongs in a robust frontend API client?

Model answer

Centralize base URLs, headers, authentication behavior, cancellation, and consistent error translation. Check response.ok because fetch resolves normally for HTTP errors such as 404 or 500; network failures reject. Handle 204 without trying to parse an empty JSON body, and account for invalid or unexpected content. Treat decoded JSON as unknown until runtime validation establishes the expected shape. Present loading, empty, success, and failure states separately. Retry only appropriate failures, and never expose server secrets in user messages.

Interview example · explanatory excerpt
// Transport excerpt; validate the returned unknown at the call site.
async function getJson(url: string, signal?: AbortSignal): Promise<unknown> {
  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  if (response.status === 204) return undefined;
  return response.json();
}
Follow-up + answer cue

Does a TypeScript generic on fetch validate JSON? → No; generated types or generics still need runtime validation at untrusted boundaries.

Avoid this mistake: Catching only rejected promises and assuming every resolved response succeeded.

#73
Q74How do you prevent an older search request from overwriting newer results?

Model answer

Debounce rapid input when appropriate, but also protect against out-of-order responses. Cancel obsolete requests with AbortController and/or use a request identity or active flag before committing results. Cleanup must run when inputs change or the component unmounts. A query library can manage keys, cancellation, and caching, but still requires correct configuration. Ignore expected aborts and show genuine failures. Cancellation reduces wasted work but does not guarantee the server never processed the request.

Follow-up + answer cue

Does debounce alone solve the race? → No; earlier and later requests can still finish in reverse order.

Avoid this mistake: Treating all aborted requests as user-visible errors or assuming completion order matches start order.

#74
Q75How do you handle optimistic updates, retries, and expired authentication?

Model answer

Use optimistic updates when the action is reversible and failure is manageable. Keep rollback/reconciliation data, account for overlapping mutations, and refetch or apply the authoritative response. For critical actions such as charging money, show a pending state and rely on server idempotency. Retry transient requests within a budget; preserve a mutation's idempotency key. Coordinate token renewal so many 401 responses do not trigger a refresh storm, retry at most under a defined policy, and require login when renewal fails.

Follow-up + answer cue

Is every 403 a reason to refresh tokens? → No; it often means authenticated access is forbidden, so renewal will not grant the missing permission.

Avoid this mistake: Automatically retrying every POST or rolling back a newer change with an older failed mutation.

Q76Design an order checkout flow using React, ASP.NET Core, SQL Server, and events.

Model answer

Clarify inventory reservation, payment timing, traffic, and consistency requirements. React sends a validated intent with an idempotency key. Q77The same payment event arrives twice, and the provider times out after charging. How do you prevent a second charge?

Model answer

Assign a stable operation key to the business payment and pass it to a provider that supports idempotency. Persist a payment state machine and enforce uniqueness for the operation/message. On timeout, record an unknown or pending result; query/reconcile with the provider using its reference and key before any new attempt. Deduplicating local messages alone cannot close the crash window between an external charge and a local commit. If the provider lacks idempotency and lookup guarantees, state that limitation and define reconciliation/manual resolution rather than promise exactly-once charging.

Follow-up + answer cue

What does a retry use? → The same logical operation key, subject to the provider's documented retention and semantics.

Avoid this mistake: Assuming a timeout means no charge happened, or relying on an in-memory HashSet for deduplication.

Q78An API's p95 latency jumps from 200 ms to 2 seconds. Walk me through your investigation.

Model answer

Confirm scope, timing, affected endpoints, deployment changes, traffic, and error rate. Trace representative slow requests to separate queueing, application work, SQL, and remote calls. Check connection/thread-pool pressure, allocations/GC, query count and plan changes, lock waits, and downstream timeouts. Form a hypothesis from evidence; reproduce safely and change one relevant variable. A new N+1 query might need projection or a bounded eager load; a dependency overload might need concurrency limits. Verify p50/p95/p99 and errors under comparable load, then monitor the rollout.

Follow-up + answer cue

Would you add a cache immediately? → No; it may hide the cause, create stale-data bugs, or amplify load on cache misses.

Avoid this mistake: Blaming the language/runtime without traces or reporting only average latency.

Q80A React results screen shows stale data and allows another user's record to be opened. How do you fix and test it?

Model answer

Treat these as separate correctness and authorization defects. Use user/tenant-aware query keys, clear or segregate cached private data when identity changes, cancel obsolete reads, and reject stale responses before updating the UI. Keep selected IDs consistent with the current result set. On the API, derive identity from validated authentication and enforce record ownership/tenant policy; a frontend cache fix is not an access boundary. Test rapid filter changes, logout/login as another user, delayed responses, direct URL navigation, and crafted requests to another user's ID.

Which tests matter at each layer? → UI behavior tests for races and identity changes; API integration tests for 401/403/404 policy and cross-tenant access.
