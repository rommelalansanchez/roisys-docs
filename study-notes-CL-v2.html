Expert-level C#

C# is a statically typed, object-oriented language that also supports functional style. "Expert-level" means you know how the language maps to the runtime: memory, allocations, async execution and type-system features, so you can write code that is both clean and fast.

Key concepts

  • Value vs reference types: structs copy by value, classes by reference; boxing allocates.
  • Records: immutable types with value equality and with expressions.
  • async/await: compiler-generated state machines; Task, ValueTask, CancellationToken.
  • Generics with constraints, covariance (out) and contravariance (in).
  • Pattern matching and switch expressions; nullable reference types.
  • Span<T> / Memory<T> for allocation-free slicing of data.
  • Garbage collector generations, IDisposable, using.
  • LINQ, delegates, lambdas, extension methods, source generators.

Where you use it

  • Web APIs and microservices with ASP.NET Core.
  • Background workers, message consumers, Azure Functions.
  • Desktop (WPF, WinUI, MAUI) and games (Unity).
  • Performance-sensitive code: parsers, high-throughput services, where allocations matter.

Example: modern C# in one snippet

public sealed record Order(Guid Id, decimal Total, OrderStatus Status);

public static string Describe(Order o) => o switch
{
    { Status: OrderStatus.Cancelled }      => "Cancelled",
    { Total: > 1_000m }                    => "Large order",
    _                                      => "Standard order"
};

public async Task<Order?> GetAsync(Guid id, CancellationToken ct)
{
    await using var conn = await _factory.OpenAsync(ct);
    return await conn.QuerySingleOrDefaultAsync<Order>(Sql, new { id }, ct);
}

var discounted = order with { Total = order.Total * 0.9m };  // non-destructive copy

Keep in mind: never block on async code with .Result or .Wait(); pass CancellationToken all the way down; prefer immutability for data that crosses boundaries.

.NET 8 / 9

.NET is Microsoft's open-source, cross-platform runtime and libraries for C#. A new version ships every November. Even-numbered versions are Long-Term Support (LTS), odd-numbered are Standard-Term Support (STS). .NET 8 (LTS, 2023) and .NET 9 (STS, 2024) both reach end of support in November 2026; .NET 10 (LTS, November 2025) is the current long-term version.

.NET 8 highlights

  • C# 12: primary constructors, collection expressions [1, 2, 3].
  • Native AOT for ASP.NET Core minimal APIs.
  • Keyed services in dependency injection.
  • TimeProvider for testable time; FrozenDictionary.
  • IExceptionHandler, Identity API endpoints, built-in metrics.

.NET 9 highlights

  • HybridCache: in-memory + distributed cache with stampede protection.
  • Built-in OpenAPI generation (AddOpenApi), replacing Swashbuckle in templates.
  • C# 13: params collections, the Lock type.
  • LINQ CountBy, AggregateBy, Index; Task.WhenEach.
  • Runtime and GC performance improvements.

Example: primary constructor + keyed service + HybridCache

builder.Services.AddKeyedSingleton<IFileStore, BlobFileStore>("blob");
builder.Services.AddHybridCache();

public class ReportService(
    [FromKeyedServices("blob")] IFileStore store,
    HybridCache cache)
{
    public Task<Report> GetAsync(int id, CancellationToken ct) =>
        cache.GetOrCreateAsync($"report:{id}",
            async token => await store.LoadReportAsync(id, token), cancellationToken: ct).AsTask();
}

Keep in mind: companies plan upgrades around LTS releases. Knowing the support timeline and the upgrade path (target framework change, package updates, breaking changes list) is part of a senior role.

ASP.NET Core

ASP.NET Core is the web framework of .NET. It hosts HTTP APIs, web apps (MVC, Razor Pages, Blazor), real-time apps (SignalR) and gRPC services on the Kestrel web server. Every request flows through a configurable middleware pipeline before reaching an endpoint.

Key concepts

  • Program.cs / WebApplication builder: register services, then configure the pipeline.
  • Middleware: ordered components (exception handling, CORS, auth, rate limiting).
  • Endpoints: controllers or minimal APIs, route groups, filters.
  • Model binding and validation; ProblemDetails for errors.
  • Configuration (appsettings, env vars, Key Vault) and the Options pattern.
  • Hosted services for background work; health checks.
  • Built-in DI, logging, output caching, rate limiting.

Where you use it

  • REST/JSON APIs consumed by React or mobile apps.
  • Backends-for-Frontends (BFF) handling login and token storage.
  • Internal gRPC services and real-time notifications with SignalR.
  • API gateways built with YARP.

Example: a minimal API with a route group

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddDbContext<AppDb>(o => o.UseSqlServer(builder.Configuration.GetConnectionString("Db")));
builder.Services.AddProblemDetails();
builder.Services.AddAuthentication().AddJwtBearer();
builder.Services.AddAuthorization();

var app = builder.Build();
app.UseExceptionHandler();
app.UseAuthentication();
app.UseAuthorization();

var orders = app.MapGroup("/api/orders").RequireAuthorization();
orders.MapGet("/{id:guid}", async (Guid id, AppDb db, CancellationToken ct) =>
    await db.Orders.FindAsync([id], ct) is { } o ? TypedResults.Ok(o) : Results.NotFound());

app.Run();

Keep in mind: middleware order matters (exception handler first, authentication before authorization). Inside the request, everything should be async and honor the request's CancellationToken.

REST API Development

REST (Representational State Transfer) is an architectural style for HTTP APIs. You expose resources at URLs, act on them with standard HTTP methods, and report results with status codes. The goal is a predictable, cacheable, stateless contract that any client can consume.

Key concepts

  • Resources as nouns: /customers/7/orders.
  • Verbs: GET (read), POST (create), PUT (replace), PATCH (partial update), DELETE.
  • Idempotency: GET, PUT, DELETE can be repeated safely; POST can't (use an Idempotency-Key).
  • Status codes: 200, 201, 204, 400, 401, 403, 404, 409, 422, 429, 500.
  • Statelessness: each request carries its own auth (token or cookie).
  • Versioning, pagination, filtering, ETags for concurrency and caching.
  • OpenAPI documents the contract.

Where you use it

  • Public APIs for partners and mobile apps.
  • The contract between a React SPA and its backend.
  • Integration between services when a synchronous answer is needed.

Example: a well-designed endpoint set

RequestMeaningSuccess response
GET /orders?status=open&page=2&pageSize=20List with filter and pagination200 + items and paging info
GET /orders/42One order200, or 404 if missing
POST /ordersCreate201 + Location: /orders/43

Keep in mind: consistency matters more than perfection. Use the same error format (ProblemDetails), naming, paging and date format across every endpoint, and never make a breaking change without a new version.

Microservices Architecture

Microservices split a system into small, independently deployable services, each owning one business capability and its own data. Teams can release and scale each service separately, at the cost of the complexity that comes with any distributed system.

Key concepts

  • Service per business capability (Orders, Payments, Catalog), aligned with DDD bounded contexts.
  • Database per service: no shared tables.
  • Communication: synchronous (REST, gRPC) or asynchronous (messages, events).
  • API Gateway (YARP, Azure API Management) as a single entry point.
  • Resilience: timeouts, retries, circuit breakers (Polly).
  • Distributed transactions via Sagas and the outbox pattern.
  • Observability: tracing, metrics, logs with OpenTelemetry.
  • Containers and orchestration (Docker, Kubernetes).

Use cases and trade-offs

  • E-commerce: catalog scales for traffic peaks independently from payments.
  • Large organizations where many teams must deploy without coordinating.
  • Parts with very different load or technology needs.
  • Not a fit for small teams or new products: a modular monolith is simpler and can be split later.

Example: placing an order across services

React SPA ──► API Gateway ──► Orders API ──(saves order + outbox row)──► SQL Server
                                   │
                                   └─ publishes OrderPlaced ──► Service Bus topic
                                                                  ├─► Payments service: charges card → PaymentCompleted
                                                                  ├─► Inventory service: reserves stock → StockReserved
                                                                  └─► Notifications service: sends email
If payment fails → PaymentFailed → Inventory releases stock (compensation) → Orders marks order Cancelled

Keep in mind: a "distributed monolith" (services that must deploy together or share a database) gets the costs of microservices without the benefits.

Event-Driven Architecture

In an event-driven architecture, components communicate by publishing events (facts about something that happened, like OrderPlaced) to a message broker. Other components subscribe and react on their own schedule. Producers don't know or wait for consumers, which decouples services and absorbs load spikes.

Key concepts

  • Event vs command: events say what happened (many listeners); commands ask one handler to do something.
  • Brokers: RabbitMQ, Azure Service Bus, Apache Kafka, AWS SQS/SNS, Azure Event Hubs.
  • Queues (one consumer per message) vs topics (publish/subscribe).
  • At-least-once delivery: duplicates happen, so consumers must be idempotent.
  • Outbox pattern for reliable publishing; dead-letter queues for failures.
  • Ordering per entity with partition keys or sessions.
  • Event sourcing and CQRS as related, optional patterns.

Where you use it

  • Integrating microservices without tight coupling.
  • Background processing: emails, PDFs, image resizing.
  • Real-time pipelines: IoT telemetry, clickstreams (Kafka, Event Hubs).
  • Audit trails and updating read models or search indexes.

Example: an idempotent consumer with MassTransit

public record OrderPlaced(Guid OrderId, Guid CustomerId, decimal Total);

public class SendConfirmationEmail(AppDb db, IEmailSender email) : IConsumer<OrderPlaced>
{
    public async Task Consume(ConsumeContext<OrderPlaced> ctx)
    {
        var msgId = ctx.MessageId!.Value;
        if (await db.ProcessedMessages.AnyAsync(m => m.Id == msgId)) return;   // duplicate: skip

        await email.SendOrderConfirmationAsync(ctx.Message.OrderId);
        db.ProcessedMessages.Add(new ProcessedMessage(msgId));
        await db.SaveChangesAsync();
    }
}

Keep in mind: the system becomes eventually consistent. Design the UI and business rules to tolerate a short delay, and add correlation IDs so you can trace a flow across services.

Entity Framework Core

EF Core is the object-relational mapper (ORM) for .NET. You work with C# classes and LINQ, and EF Core translates them into SQL, tracks changes to loaded objects, and saves them back. It supports SQL Server, PostgreSQL, SQLite, Cosmos DB and more.

Key concepts

  • DbContext (unit of work) and DbSet<T> (tables).
  • Fluent configuration with IEntityTypeConfiguration<T>.
  • Migrations to evolve the schema.
  • Change tracking; AsNoTracking for reads.
  • Loading: Include, projection with Select, split queries.
  • Concurrency tokens (rowversion).
  • Bulk operations: ExecuteUpdate, ExecuteDelete.
  • Global query filters (soft delete, multi-tenant), owned types, value conversions.

Where you use it

  • Most CRUD and business data access in .NET apps.
  • The write side of CQRS, while reads may use projections or Dapper.
  • Multi-tenant SaaS with global filters per tenant.
  • Integration tests with Testcontainers running a real SQL Server.

Example: configuration, efficient read and bulk update

public class OrderConfig : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.Property(o => o.Total).HasPrecision(18, 2);
        b.Property(o => o.RowVersion).IsRowVersion();
        b.HasMany(o => o.Lines).WithOne().OnDelete(DeleteBehavior.Cascade);
        b.HasQueryFilter(o => !o.IsDeleted);
    }
}

// Read: project only the columns you need, no tracking, one SQL query
var summary = await db.Orders
    .Where(o => o.CustomerId == customerId)
    .Select(o => new OrderSummary(o.Id, o.Total, o.Lines.Count))
    .ToListAsync(ct);

// Bulk update: a single UPDATE statement, no entities loaded
await db.Orders.Where(o => o.Status == Status.Draft && o.CreatedAt < cutoff)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, Status.Expired), ct);

Keep in mind: log the generated SQL in development. Most EF performance problems are N+1 queries, loading whole entities when a projection would do, and tracking data you never modify.

LINQ

LINQ (Language Integrated Query) lets you query collections, databases and other sources with the same C# operators: Where, Select, GroupBy, OrderBy and many more. Over in-memory data it runs as C# code; over IQueryable (EF Core) it is translated into SQL.

Key concepts

  • Deferred execution: the query runs only when enumerated.
  • Immediate operators: ToList, Count, First, Any, Sum.
  • IEnumerable (in memory, delegates) vs IQueryable (expression trees, translated).
  • Projection (Select), flattening (SelectMany), grouping, joins.
  • Newer helpers: DistinctBy, MaxBy, Chunk, CountBy, Index.
  • Method syntax (most common) and query syntax.

Where you use it

  • Database queries through EF Core.
  • Transforming API results and DTOs.
  • Reports and aggregations over in-memory data.
  • Validation (Any, All) and lookups (ToDictionary, ToLookup).

Example: common operations

// Top 3 customers by revenue in a date range
var top = orders
    .Where(o => o.Date >= from && o.Date < to)
    .GroupBy(o => o.CustomerId)
    .Select(g => new { CustomerId = g.Key, Revenue = g.Sum(o => o.Total), Count = g.Count() })
    .OrderByDescending(x => x.Revenue)
    .Take(3)
    .ToList();

// Flatten all order lines and count products sold
var unitsByProduct = orders.SelectMany(o => o.Lines)
    .GroupBy(l => l.ProductId)
    .ToDictionary(g => g.Key, g => g.Sum(l => l.Quantity));

// Existence check: Any() stops at the first match
bool hasOverdue = invoices.Any(i => i.DueDate < today && !i.Paid);

Keep in mind: enumerating the same query twice runs it twice. Calling ToList() too early on an EF query moves filtering from the database into memory.

SQL Server

SQL Server is Microsoft's relational database. Data is stored in tables with schemas, relationships and constraints, and queried with T-SQL. It provides ACID transactions, indexing, a cost-based query optimizer, and tools for monitoring performance. In the cloud it runs as Azure SQL Database or Azure SQL Managed Instance.

Key concepts

  • Normalization, primary and foreign keys, constraints.
  • Indexes: clustered, nonclustered, covering (INCLUDE), filtered, columnstore.
  • Execution plans: seeks vs scans, key lookups, statistics.
  • SARGable predicates that can use indexes.
  • Transactions and isolation levels, RCSI, locking, deadlocks.
  • Window functions, CTEs, stored procedures, views.
  • Query Store to track plan regressions; parameter sniffing.

Where you use it

  • Transactional systems: orders, billing, inventory, accounts.
  • Reporting with views, indexed views, columnstore indexes.
  • Data needing strong consistency and complex joins.

Example: index for a common query, plus a window function

-- Query: a customer's recent orders
SELECT OrderId, OrderDate, Total
FROM dbo.Orders
WHERE CustomerId = @CustomerId AND OrderDate >= @From
ORDER BY OrderDate DESC;

-- Index that lets SQL Server seek and avoid key lookups
CREATE NONCLUSTERED INDEX IX_Orders_Customer_Date
ON dbo.Orders (CustomerId, OrderDate DESC) INCLUDE (Total);

-- Running total per customer
SELECT CustomerId, OrderDate, Total,
       SUM(Total) OVER (PARTITION BY CustomerId ORDER BY OrderDate
                        ROWS UNBOUNDED PRECEDING) AS RunningTotal
FROM dbo.Orders;

-- Not SARGable (can't seek):  WHERE YEAR(OrderDate) = 2026
-- SARGable alternative:        WHERE OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01'

Keep in mind: every index speeds up reads and slows down writes. Design indexes from real query patterns and confirm them in the execution plan.

NoSQL Databases

NoSQL databases store data in models other than relational tables: documents, key-value pairs, wide columns or graphs. They trade some relational features (joins, cross-entity transactions) for horizontal scalability, flexible schemas and very fast access for known query patterns.

Types and products

  • Document: Azure Cosmos DB, MongoDB. JSON documents.
  • Key-value: Redis, DynamoDB. Fast lookup by key.
  • Wide-column: Cassandra. Huge write volumes, time series.
  • Graph: Neo4j. Relationships and traversal.
  • Search: Elasticsearch, Azure AI Search. Full-text search.

Where you use it

  • Product catalogs with varied attributes (document).
  • Caching, sessions, rate limits, leaderboards (Redis).
  • User profiles, carts, IoT events at global scale (Cosmos DB, DynamoDB).
  • Recommendations and fraud detection (graph).

Key modeling ideas

  • Model for the queries: store data the way it's read. Embed what's read together (an order and its lines); reference what's large or shared.
  • Partition key (Cosmos DB, DynamoDB) decides scale and cost: choose high cardinality and include it in most queries.
  • Consistency levels: Cosmos offers Strong, Bounded Staleness, Session, Consistent Prefix and Eventual.
  • CAP theorem: during a network partition you choose consistency or availability.

Dependency Injection

Dependency Injection (DI) means a class receives the objects it depends on (usually through its constructor) instead of creating them. A container builds the object graph for you. This makes code loosely coupled, testable with fakes, and configurable in one place. ASP.NET Core has a DI container built in.

Key concepts

  • Lifetimes: Transient (always new), Scoped (one per request), Singleton (one per app).
  • Captive dependency: a singleton holding a scoped service is a bug.
  • Constructor injection as the default.
  • Multiple implementations: IEnumerable<T>, keyed services.
  • IServiceScopeFactory for scoped services inside singletons and background jobs.
  • Decorators (Scrutor) for cross-cutting behavior.

Where you use it

  • Swapping implementations per environment (real email vs fake email).
  • Unit tests with mocks (Moq, NSubstitute).
  • Wiring Clean Architecture layers together in the composition root.
  • Plugin-like strategies chosen at runtime.

Example

// Registration (composition root)
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddSingleton(TimeProvider.System);
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();

// Consumer: depends on abstractions, receives them via constructor
public class PlaceOrderHandler(IOrderRepository repo, IEmailSender email, TimeProvider clock)
{
    public async Task HandleAsync(PlaceOrder cmd, CancellationToken ct)
    {
        var order = Order.Create(cmd.CustomerId, cmd.Lines, clock.GetUtcNow());
        await repo.AddAsync(order, ct);
        await email.SendAsync(cmd.CustomerEmail, "Order received", ct);
    }
}

// Test: inject fakes
var handler = new PlaceOrderHandler(new InMemoryOrderRepo(), new FakeEmailSender(), new FakeTimeProvider());

Keep in mind: avoid the Service Locator anti-pattern (resolving from IServiceProvider all over the code); it hides dependencies.

Clean Architecture

Clean Architecture organizes code into layers where dependencies point inward toward the business rules. The domain and use cases know nothing about databases, frameworks or UI; those details live in outer layers and plug in through interfaces. The result is business logic you can test and evolve independently of technology.

The layers

  • Domain: entities, value objects, domain events, business rules.
  • Application: use cases (commands, queries, handlers), interfaces such as IOrderRepository, DTOs, validation.
  • Infrastructure: EF Core, email, storage, message brokers, external APIs.
  • Presentation: API endpoints, composition root.

Use cases and trade-offs

  • Long-lived business systems with complex rules.
  • Apps likely to change infrastructure (on-prem SQL to cloud, one broker to another).
  • High unit-test coverage of business logic.
  • Cost: more projects, interfaces and mapping. For simple CRUD, Vertical Slice Architecture (organize by feature) is often lighter.

Example: solution structure

src/
  Shop.Domain/            Order.cs, Money.cs, OrderPlaced.cs        (no references)
  Shop.Application/       Orders/PlaceOrder/PlaceOrderCommand.cs
                          Orders/PlaceOrder/PlaceOrderHandler.cs
                          Abstractions/IOrderRepository.cs, IEmailSender.cs
                                                                     → references Domain
  Shop.Infrastructure/    Persistence/AppDbContext.cs, SqlOrderRepository.cs
                          Email/SmtpEmailSender.cs                    → references Application
  Shop.Api/               Endpoints/OrderEndpoints.cs, Program.cs    → references Application + Infrastructure
tests/
  Shop.Domain.Tests/  Shop.Application.Tests/  Shop.Api.IntegrationTests/

Keep in mind: CQRS often fits here (commands through the domain, queries straight to read models). MediatR moved to a commercial license in 2025, so plain handler classes are a common alternative.

Domain-Driven Design (DDD)

DDD is an approach to complex software where the code models the business domain closely, in the language that domain experts use. It has a strategic part (how to split a large domain into clear boundaries) and a tactical part (building blocks for the model inside each boundary).

Strategic concepts

  • Ubiquitous language: one shared vocabulary in conversations and code.
  • Bounded context: a boundary where a model is consistent. "Customer" in Sales differs from "Customer" in Support.
  • Subdomains: core (competitive advantage), supporting, generic.
  • Context map: how contexts integrate (anti-corruption layer, shared kernel).

Tactical concepts

  • Entity: has identity (Order #42).
  • Value object: defined by values, immutable (Money, Address).
  • Aggregate: consistency boundary with one root; reference others by ID.
  • Domain events: something meaningful happened (OrderShipped).
  • Domain services, repositories, factories.

Example: an aggregate root protecting its rules

public sealed record Money(decimal Amount, string Currency);

public class Order : AggregateRoot
{
    private readonly List<OrderLine> _lines = [];
    public Guid Id { get; private set; }
    public Guid CustomerId { get; private set; }        // reference by ID, not object
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;
    public IReadOnlyList<OrderLine> Lines => _lines;

    public void AddLine(Guid productId, int qty, Money price)
    {
        if (Status != OrderStatus.Draft) throw new DomainException("Only draft orders can change.");
        if (qty <= 0) throw new DomainException("Quantity must be positive.");
        _lines.Add(new OrderLine(productId, qty, price));
    }

    public void Submit()
    {
        if (_lines.Count == 0) throw new DomainException("An order needs at least one line.");
        Status = OrderStatus.Submitted;
        Raise(new OrderSubmitted(Id, CustomerId));
    }
}

Keep in mind: DDD pays off in complex domains (insurance, logistics, banking). For simple CRUD, a rich domain model is overhead. Bounded contexts are also the natural seams for microservices.

SOLID Principles

SOLID is five object-oriented design principles that keep code easy to change, test and extend. They guide where responsibilities live and how classes depend on each other.

PrincipleMeaningExample
Single ResponsibilityA class has one reason to change.Split an InvoiceService that calculates, renders PDF and emails into three classes.
Open/ClosedExtend behavior without modifying existing code.New discount types implement IDiscountRule instead of adding cases to a switch.
Liskov SubstitutionSubtypes must work wherever the base type is expected.A ReadOnlyRepository that throws on Save() violates it; split the interface instead.
Interface SegregationPrefer small, specific interfaces.IOrderReader and IOrderWriter instead of one 20-method interface.
Dependency InversionDepend on abstractions; high-level code owns the interface.The Application layer defines IEmailSender; Infrastructure implements it.

Example: Open/Closed with a strategy

public interface IDiscountRule { bool Applies(Order o); decimal Discount(Order o); }

public class LoyaltyDiscount : IDiscountRule
{
    public bool Applies(Order o) => o.Customer.YearsActive >= 3;
    public decimal Discount(Order o) => o.Total * 0.05m;
}

public class PricingService(IEnumerable<IDiscountRule> rules)
{
    public decimal FinalPrice(Order o) => o.Total - rules.Where(r => r.Applies(o)).Sum(r => r.Discount(o));
}
// A new promotion = a new class + one DI registration. PricingService never changes.

Keep in mind: SOLID is a guide, not a goal. Interfaces for every class with a single implementation add noise; balance with YAGNI and KISS.

Authentication & Authorization (OAuth2, OIDC, JWT)

Authentication proves who a user is; authorization decides what they can do. Modern apps delegate login to an identity provider (Microsoft Entra ID, Auth0, Okta, Keycloak, Duende IdentityServer) using open standards: OAuth 2.0 for delegated API access, OpenID Connect for login and identity, and JWT as the token format.

Key concepts

  • OAuth 2.0: a client gets an access token to call an API.
  • OIDC: adds an ID token describing the logged-in user.
  • Flows: Authorization Code + PKCE (web, SPA, mobile); Client Credentials (service to service). Implicit and password flows are deprecated.
  • JWT: header.payload.signature; claims like sub, iss, aud, exp, scopes, roles.
  • Refresh tokens with rotation; short-lived access tokens.
  • Authorization models: roles, claims, policies, resource-based checks.
  • BFF pattern keeps tokens off the browser.

Where you use it

  • Single sign-on with corporate accounts (Entra ID).
  • Protecting APIs called by a React SPA.
  • Machine-to-machine calls between microservices.
  • Multi-tenant SaaS with per-tenant permissions.

Example: the login flow and API protection

1. User clicks "Sign in" in the React app
2. App redirects to the identity provider with a PKCE code challenge
3. User logs in; provider redirects back with an authorization code
4. App (or BFF) exchanges code + verifier for ID token, access token, refresh token
5. API calls send: Authorization: Bearer <access token>
6. API validates signature, issuer, audience and expiry, then checks policies
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o => { o.Authority = "https://login.example.com/"; o.Audience = "orders-api"; });

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("CanRefund", p => p.RequireClaim("scope", "orders.refund").RequireRole("Supervisor"));

app.MapPost("/orders/{id}/refund", RefundOrder).RequireAuthorization("CanRefund");

Keep in mind: a JWT is signed, not encrypted, so never put secrets in it. Don't store tokens in localStorage; prefer a BFF with HttpOnly, Secure, SameSite cookies.

ReactJS

React is a JavaScript library for building user interfaces from components: functions that take props and state and return markup (JSX). When data changes, React re-renders the affected components and efficiently updates only the parts of the DOM that changed.

Key concepts

  • Components, props, state; one-way data flow from parent to child.
  • Hooks: useState, useEffect, useRef, useMemo, useCallback, useContext, useReducer.
  • Custom hooks to share logic.
  • Keys in lists; reconciliation.
  • Controlled vs uncontrolled form inputs.
  • React 18/19: concurrent rendering, transitions, Suspense, Actions, useOptimistic, use(), Server Components, React Compiler.
  • Ecosystem: React Router, TanStack Query, React Hook Form, Vite, Next.js.

Where you use it

  • Single-page apps and dashboards over an ASP.NET Core API.
  • Admin back-offices and internal tools.
  • Server-rendered sites with Next.js.
  • Mobile apps with React Native.

Example: a component with state, effect and a custom hook

function useDebounce<T>(value: T, ms = 300) {
  const [v, setV] = useState(value);
  useEffect(() => { const t = setTimeout(() => setV(value), ms); return () => clearTimeout(t); }, [value, ms]);
  return v;
}

export function ProductSearch() {
  const [term, setTerm] = useState('');
  const debounced = useDebounce(term);
  const { data = [], isLoading } = useQuery({
    queryKey: ['products', debounced],
    queryFn: ({ signal }) => api.searchProducts(debounced, signal),
    enabled: debounced.length > 1,
  });

  return (
    <>
      <label htmlFor="q">Search products</label>
      <input id="q" value={term} onChange={e => setTerm(e.target.value)} />
      {isLoading ? <p>Loading…</p> : (
        <ul>{data.map(p => <li key={p.id}>{p.name} · ${p.price}</li>)}</ul>
      )}
    </>
  );
}

Keep in mind: derive values during render instead of syncing them with effects, keep state as close as possible to where it's used, and never use an array index as a key for lists that change.

TypeScript

TypeScript is JavaScript with a static type system. It compiles to plain JavaScript; the types exist only at build time to catch errors early, power editor autocomplete, and document intent. It's the standard for professional React work.

Key concepts

State Management (Redux, Context API, or similar)

State management is how a React app stores and shares data that changes over time, and how components react to those changes. The main skill is choosing the right home for each kind of state, from local component state up to a global store, and treating server data as its own category.

Kinds of state and tools

  • Local UI state: useState, useReducer.
  • Shared client state: Context API, Redux Toolkit, Zustand, Jotai.
  • Server state: TanStack Query, RTK Query (caching, refetch, invalidation).
  • URL state: filters and pages in search params (React Router).
  • Form state: React Hook Form.

When to use what

  • Context: low-frequency global values (theme, locale, current user).
  • Redux Toolkit: large apps, lots of shared and interdependent state, many developers, need for DevTools and conventions.
  • Zustand: small, simple global stores with selectors.
  • TanStack Query: almost all API data; often removes the need for a global store.

API Integration

API integration is how the front end talks to backends: making HTTP requests, handling loading and errors, attaching authentication, caching results and keeping types in sync with the server's contract. For this role, the backend is usually your own ASP.NET Core API.

Key concepts

  • HTTP clients: fetch (doesn't reject on 4xx/5xx) or Axios (interceptors).
  • An API layer: one module per resource, not fetch calls scattered in components.
  • Data fetching libraries: TanStack Query, RTK Query, SWR.
  • Loading, error, empty states; retries; optimistic updates.
  • Cancellation with AbortController; avoiding race conditions.
  • CORS and preflight requests.
  • Auth: cookies via BFF or bearer tokens with refresh on 401.
  • Typed clients generated from OpenAPI (NSwag, Orval, openapi-typescript); Zod validation.

Where you use it

  • Every screen that reads or saves data.
  • Search-as-you-type, infinite scroll, file uploads.
  • Real-time updates with SignalR or WebSockets.

Example: typed client + TanStack Query with optimistic update

// api/client.ts
export async function http<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`/api${path}`, { credentials: 'include', ...init,
    headers: { 'Content-Type': 'application/json', ...init?.headers } });
  if (!res.ok) throw await res.json();          // ProblemDetails from ASP.NET Core
  return res.status === 204 ? (undefined as T) : res.json();
}
export const ordersApi = {
  list: (signal?: AbortSignal) => http<Order[]>('/orders', { signal }),
  markPaid: (id: string) => http<void>(`/orders/${id}/payment`, { method: 'POST' }),
};

// In a component
const qc = useQueryClient();
const { data, isLoading, error } = useQuery({ queryKey: ['orders'], queryFn: ({ signal }) => ordersApi.list(signal) });
const markPaid = useMutation({
  mutationFn: ordersApi.markPaid,
  onMutate: async id => {                       // optimistic update
    await qc.cancelQueries({ queryKey: ['orders'] });
    const prev = qc.getQueryData<Order[]>(['orders']);
    qc.setQueryData<Order[]>(['orders'], o => o?.map(x => x.id === id ? { ...x, status: 'Paid' } : x));
    return { prev };
  },
  onError: (_e, _id, ctx) => qc.setQueryData(['orders'], ctx?.prev),   // roll back
  onSettled: () => qc.invalidateQueries({ queryKey: ['orders'] }),
});

Keep in mind: treat 401 (sign in again) and 403 (not allowed) differently, show field-level validation errors from ProblemDetails, and never trust that the response matches your TypeScript types.

Git is the version control system behind nearly all modern development, hosted on GitHub, Azure Repos or GitLab. Teams agree on a branching strategy and use pull requests with code review and automated checks before merging.

CI/CD Pipelines

Continuous Integration builds and tests every change automatically. Continuous Delivery/Deployment packages the result and promotes it through environments (dev, staging, production), often with approvals. The most used tools for .NET teams are GitHub Actions and Azure DevOps Pipelines; others include GitLab CI and Jenkins.

Typical pipeline stages

  • Restore, build, run unit and integration tests.
  • Static analysis and security scans (SonarQube, CodeQL, Dependabot).
  • Build the React app (npm ci && npm run build) and a Docker image.
  • Push the image to a registry (ACR, GHCR, ECR).
  • Deploy to dev automatically; staging and production with approvals.
  • Run EF Core migration scripts; smoke tests; rollback plan.

Deployment strategies

  • Rolling: replace instances gradually.
  • Blue-green: switch traffic between two identical environments (App Service deployment slots).
  • Canary: send a small percentage of traffic to the new version first.
  • Feature flags (Azure App Configuration, LaunchDarkly) to decouple deploy from release.

DevSecOps & Secrets Management

DevSecOps builds security into every step of delivery instead of checking it at the end. In practice: no secrets in code, automated scanning in pipelines, least-privilege access, and secure defaults in the cloud.

Practices and tools

  • Secrets: Azure Key Vault, AWS Secrets Manager, HashiCorp Vault; User Secrets locally.
  • Managed identities / IAM roles instead of connection strings with passwords.
  • Dependency scanning: Dependabot, dotnet list package --vulnerable, npm audit.
  • Static analysis (SAST): CodeQL, SonarQube; secret scanning in repos.
  • Container image scanning: Trivy, Microsoft Defender for Cloud.
